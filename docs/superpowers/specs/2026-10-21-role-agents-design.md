# 역할자(PM·개발자·QA …) 자동 검토 (설계)

작성일: 2026-10-21 · 상태: 사용자 승인 대기 · 대상: `/home/hyeanjae/projects/claude-office` (기존 Claude Office에 추가)

## 1. 의도와 이유

사용자는 여러 프로젝트에서 Claude Code로 작업한다. 지금은 Claude가 한 작업이 요구사항에 맞는지, 코드에 문제가 없는지, 검증됐는지를 사용자가 직접 확인해야 한다. 사용자가 작업을 진행하는 동안 **PM·개발자·QA 같은 역할자가 자동으로 그 작업을 확인**하고, 그 모습이 사무실 화면에 팀원처럼 나타나 일하고, 결과가 보고서로 남기를 원한다.

- Paperclip 같은 외부 도구는 쓰지 않고, 같은 방식을 **이 PC의 로컬 Claude Code만으로** 구현한다.
- **모든 프로젝트에 적용**한다(화면에 팀으로 올린 프로젝트뿐 아니라 이 PC에서 Claude를 쓰는 모든 프로젝트).
- 역할은 PM·개발자·QA로 한정하지 않는다. **역할 파일 하나를 추가하면 새 역할자(보안, 문서 등)가 생긴다.**

성공 기준: 사용자가 아무 설정 없이 작업하다가 화면과 보고서에서 (1) 어떤 역할자가 언제 무엇을 확인했는지, (2) 문제가 있었는지(심각도와 한 줄 설명)를 볼 수 있다. 작업 중인 코드와 세션은 역할자 때문에 절대 바뀌지 않는다.

## 2. 사용자가 직접 정한 것

- 역할자는 **실제로 자동 실행**된다(이름표만 붙이는 방식이 아니다).
- 이후 **모든 프로젝트**에 적용한다.
- 역할은 **추가할 수 있어야 한다**(PM·개발자·QA는 기본 제공).
- Paperclip은 쓰지 않는다.

## 3. 내가 정한 것 (검토 필요)

1. **전달 방식은 "보고만"으로 시작한다.** 문제를 찾아도 작업 중인 Claude 세션에는 아무것도 보내지 않는다. 화면과 보고서에만 남긴다. 세션에 자동 전달(Claude가 바로 고치게 함)은 나중에 프로젝트별 옵션으로 추가할 수 있도록 설정 자리(`deliver`)만 만들고 **기본은 `report`**. 이유: 무한 반복·비용 증가·원치 않는 수정을 피하고, 먼저 검토 품질을 눈으로 확인하기 위해서.
2. **트리거는 Claude의 응답이 끝날 때(Stop 신호)**, 그 사이에 의미 있는 작업이 있었을 때만 한다(§5.1).
3. **역할자는 읽기 전용 `claude -p` 프로세스**로 실행한다(사용자의 Claude 구독 사용, API 키 없음). 파일을 읽고 `git diff`를 볼 수 있지만 쓰거나 실행할 수 없다.
4. **보고서는 중앙 폴더**에 저장한다(프로젝트 폴더를 더럽히지 않음): `claude-office/data/reviews/<프로젝트>/<시각>-<역할>.json` 과 사람이 읽는 `latest.md`. `data/`는 git에서 제외.
5. **비용 제한 기본값**: 프로젝트당 쿨다운 5분, 하루 전체 40회, 역할당 시간 제한 180초. 모델은 역할 파일에서 지정(기본 `sonnet`).
6. **기본 역할 3개(PM, 개발자, QA)와 선택 역할 2개(보안, 문서)를 제공**하고, 기본으로 켜는 것은 PM·개발자·QA뿐이다. 보안·문서는 프로젝트 설정에서 켠다.
7. **원격 PC 세션은 이번 범위에서 제외**한다(원격 파일을 읽을 수 없음).

## 4. 동작 개요

```
Claude 세션(이 PC) --hook--> 서버(7410→9410) --Stop + 의미 있는 작업--> 검토 스케줄러
                                                      │ 역할마다 읽기 전용 `claude -p` 실행 (병렬)
                                                      ▼
                                      결과(JSON) → 보고서 저장 + 화면(역할자 아바타·배지·보고서 패널)
```

### 4.1 역할 정의 (확장 지점)
역할은 `claude-office/roles/<id>.md` 파일 하나다. 앞부분(frontmatter)과 본문(프롬프트)로 구성한다.

```markdown
---
name: 보안            # 화면에 표시되는 이름
color: "#e5484d"      # 화면 색
model: sonnet         # haiku | sonnet | opus 별칭
when: code            # always | code(코드 파일 변경이 있을 때) | docs(문서 변경이 있을 때)
tools: [Read, Grep, Glob]
---
당신은 보안 검토자다. … (역할 지침, 출력 형식은 시스템이 덧붙인다)
```
- 시스템은 역할 프롬프트 뒤에 **공통 출력 형식**(§4.3)과 **읽기 전용 규칙**을 항상 덧붙인다.
- `tools`는 `Read`, `Grep`, `Glob`만 허용한다. 그 밖의 도구(`Bash`, `Edit`, `Write`, `NotebookEdit` 등)가 들어 있으면 **그 역할은 거부**하고 오류로 알린다. 역할자에게는 셸 도구를 아예 주지 않는다. git 정보는 서버가 대신 만들어 프롬프트로 준다.
- 역할 추가 = 파일 추가. 사용자가 "보안 역할자 추가해줘"라고 하면 Claude가 이 파일을 만든다(문서에 예시 제공).
- 프로젝트별로 어떤 역할을 쓸지는 설정으로 정한다: `roles.default: ["pm","developer","qa"]`, 프로젝트 항목의 `roles`로 덮어쓰기. 알 수 없는 역할 id는 시작 시 오류.

### 4.2 검토 입력(문맥 묶음)
역할자에게 다음을 프롬프트로 준다(모두 비밀값 마스킹 후, 크기 제한):
- 사용자의 마지막 요청(앞 500자)과 Claude의 마지막 응답 요약(앞 2000자) — Stop·UserPromptSubmit 신호에 들어 있다.
- **이 세션이 마지막 검토 이후 편집한 파일**(Edit/Write/NotebookEdit 신호의 경로)을 git 저장소 루트별로 묶고, 각 저장소에서 `git diff HEAD -- <그 파일들>`을 서버가 만들어 준다(최대 60KB, 넘으면 파일 목록과 통계만, 새 파일은 앞부분 일부). 사용자의 예전 미커밋 작업이나 다른 세션의 편집은 포함하지 않는다. `.env`·키 파일은 내용을 제외한다.
- 저장소가 아닌 폴더의 파일은 v1에서 검토하지 않는다.
- 사용자의 최근 요청: 마지막 검토 이후 이 세션의 요청들(최대 5개, 각 300자)과 Claude의 마지막 응답(2000자). PM이 여러 턴에 걸친 요구를 판단할 수 있게 하려는 것이다.
- 역할자는 필요하면 읽기 도구로 프로젝트의 README·CLAUDE.md·관련 파일을 더 읽는다. 읽기 도구는 민감 경로(`.env*`, `~/.ssh`, `~/.aws`, `*.pem`, 키 파일)에 대한 읽기 거부 규칙을 함께 건다(구현 때 실제로 거부되는지 검증).
역할자 프로세스는 프로젝트 작업 폴더에서 `--setting-sources ''`, 최소 환경변수, `CLAUDE_OFFICE_ROLE=1`로 실행한다(hook 재귀 차단, §6).

### 4.3 역할자 출력 형식
역할자는 JSON 하나만 출력한다:
```json
{ "verdict": "ok|concern|block",
  "summary": "한 줄(60자 안팎, 한국어)",
  "findings": [ { "severity": "info|minor|major|critical", "text": "…", "file": "src/a.js", "line": 12 } ] }
```
파싱에 실패하면 원문 앞부분을 `summary`로 쓰고 `verdict: "concern"`, 보고서에 "형식 오류" 표시. 팀의 종합 판정은 가장 나쁜 판정이다.

### 4.4 화면 표현
- 검토가 시작되면 해당 팀 구역에 **역할자 아바타**가 팀원처럼 나타난다. 이름표는 역할 이름(PM·개발자·QA …), 셔츠 색은 역할 색, 말풍선은 "요구사항 확인 중" 같은 진행 문구. 끝나면 퇴근한다.
- 끝난 뒤 팀장 머리 위에 **판정 배지**가 남는다: ✓(ok) / ⚠ n(concern) / ⛔(block). 다음 검토 전까지 유지.
- 화면에 **보고서 패널**(오른쪽 위 버튼): 프로젝트별 최근 검토의 역할, 판정, 한 줄 요약, 지적 목록. 화면에 팀으로 올리지 않은 프로젝트의 검토도 여기서 본다.
- 한 팀의 역할자가 4명을 넘으면 기존 팀원 표시 규칙(최대 4명 + "+N")을 따른다.

## 5. 세부 규칙

### 5.1 언제 검토하나
Stop 신호가 올 때 아래를 모두 만족하면 검토한다.
1. 이 세션이 마지막 검토 이후 **파일 편집 도구(Edit/Write/NotebookEdit)를 1회 이상** 썼고, 그 파일이 git 저장소 안에 있다(`roles.minWrites`, 기본 1). Bash로 한 편집(`sed -i`, 포매터 등)은 v1에서 세지 않는다(알려진 한계).
2. 해당 저장소의 마지막 검토 시작 후 **쿨다운(기본 5분)**이 지났다. 쿨다운 중이면 변경은 모아 두고, **쿨다운이 끝난 시점에 세션이 30초 이상 조용하면 타이머로 검토를 시작**한다(조용하지 않으면 다음 Stop에서). 사용자가 작업을 멈춰도 마지막 변경이 검토되도록 하려는 것이다.
3. 오늘 **역할자 프로세스 수**가 일일 한도(기본 120 = 대략 검토 40회×역할 3)보다 적다. 하루는 KST 자정에 바뀌고, 카운터는 `data/reviews/_counter.json`에 저장해 재시작해도 유지한다.
4. 이 세션이 하위 에이전트를 아직 기다리는 중이 아니다(기존 "팀원이 남아 있으면 Stop은 완료가 아니다" 규칙과 같은 기준).
5. 이 이벤트가 역할자 프로세스에서 온 것이 아니다(§6).
역할마다 `when` 조건으로 한 번 더 거른다(예: `code`는 코드 파일이 바뀐 경우만).

### 5.2 프로젝트 식별과 설정
- 검토 단위(프로젝트 키)는 **편집된 파일이 속한 git 저장소 루트**다. 세션이 홈 폴더에서 열려 있어도 편집한 파일의 저장소가 기준이 되므로, 한 세션이 여러 저장소를 건드리면 저장소별로 따로 검토한다. 쿨다운은 저장소별, 일일 한도는 전체 기준이다. 역할자 프로세스와 요약기가 띄운 세션은 hook이 꺼져 있어 신호가 오지 않으므로 검토 대상이 아니다.
- 화면의 팀과 연결: 그 세션이 이미 속한 팀이 있으면 그 팀, 없으면 저장소 경로를 덮는 팀(경로 접두사), 둘 다 없으면 화면에는 나오지 않고 보고서 패널과 파일에만 남는다.
- 설정은 `config.json`의 `roles` 한 곳에 둔다: `roles.default`(기본 `["pm","developer","qa"]`), `roles.cooldownMinutes`, `roles.minWrites`, `roles.dailyLimit`, `roles.deliver`(`report`), 그리고 `roles.projects`에 **저장소 경로별 덮어쓰기**(`{"/home/me/projects/Pin-It": {"roles":["pm","developer","qa","security"]}}`). 가장 긴 경로가 이긴다. 화면 팀 항목(`projects[]`)에도 `roles`를 적을 수 있고 그것이 우선한다. 알 수 없는 역할 id는 어디에 있든 서버 시작 시 오류다.

### 5.3 실패와 한도
- 역할자가 시간 제한(180초)을 넘기거나 비정상 종료하면 그 역할은 "검토 실패(사유)"로 기록하고 재시도하지 않는다.
- 일일 한도에 걸리면 건너뛰고 보고서 패널에 "한도 도달"을 한 줄 표시한다.
- 한 번에 동시에 도는 역할자 프로세스는 최대 3개(전체)로 제한하고 나머지는 대기열에 둔다.
- 같은 저장소에서 검토가 진행 중일 때 새 Stop이 오면 새 검토를 시작하지 않고 "다시 검토 필요"로 표시해 두었다가, 진행 중인 검토가 끝나고 쿨다운이 지나면 한 번만 다시 한다. 새 프롬프트가 와도 진행 중인 검토를 취소하지 않고, 늦게 끝난 결과도 그대로 반영한다(최신 완료 결과가 배지가 된다).
- 서버를 재시작하면 진행 중이던 검토는 버린다(일일 카운터와 보고서 파일은 유지).
- 보고서 보관: 저장소마다 최근 200개 JSON만 남기고 오래된 것은 지운다. `latest.md`는 저장소별로 역할마다 가장 최근 결과를 모은 파일이다.
- 화면 전달: WebSocket 스냅샷에 팀별 판정 배지와 최근 검토 요약 목록(최근 20건)을 넣고, 지적 사항 상세는 로컬 전용 HTTP `GET /api/reviews?repo=...`로 가져온다(기존 Host/Origin 검사 적용).

## 6. 보안 · 안전 (실패로 보는 경우)

- 역할자가 **프로젝트 파일을 바꾸거나 명령을 실행하면 실패**다. 도구 허용 목록(읽기 전용)과 `--disallowedTools`(쓰기·실행 계열)를 함께 쓴다.
- 역할자 프로세스가 hook을 일으켜 **무한 반복**하면 실패다. `CLAUDE_OFFICE_ROLE=1`이면 `hook.js`는 즉시 종료한다(요약기의 기존 `CLAUDE_OFFICE_SUMMARIZER`와 같은 방식).
- **비밀값**이 보고서·화면·로그에 남으면 실패다. 프롬프트로 넘기기 전과 보고서를 쓰기 전에 모두 마스킹한다. `.env`·키 파일은 `git diff`에서도 내용을 제외한다.
- 역할자 프로세스는 사용자의 전역 설정·hook을 읽지 않는다(`--setting-sources ''`). 환경변수는 허용 목록만 전달한다.
- 보고서 폴더는 사용자만 읽을 수 있게(0700) 만든다.
- 역할 파일 로딩 시 `tools` 검증 실패, 알 수 없는 frontmatter 키, 과도한 길이(프롬프트 20KB 초과)는 거부한다.

## 7. 목표 / 비목표

**목표**: 자동 트리거, 역할 확장(파일 추가), 읽기 전용 안전성, 화면 표현, 보고서, 비용 제한.
**비목표(이번 범위 밖)**: 역할자가 코드를 고치는 기능, 작업 세션에 결과를 자동 전달(`deliver: session`), 원격 PC 세션 검토, 테스트·빌드를 역할자가 직접 실행하는 기능(QA는 코드를 읽고 diff를 보고 판단만 한다 — 나중에 프로젝트 설정 `qa.testCommand`로 확장 가능), 역할자 간 대화·토론.

## 8. 빌더에게 맡기는 것
- 역할 파일 파서의 세부(frontmatter 문법 수준), 대기열 구현, 보고서 패널의 시각 디자인, 판정 배지 모양, 진행 문구 목록, 프롬프트 문구(역할별 지침의 구체 문장은 기본 3+2개를 작성하되 사용자가 고칠 수 있음).
- 기존 구조(`src/state.js`, `src/server.js`, `public/js/scene.js`)에 맞춰 역할자를 "역할 팀원"으로 얹는 방법.

## 9. 알려진 위험
- 검토 품질: 역할자는 diff와 일부 파일만 본다. 오탐·누락이 있을 수 있어 처음엔 "참고용 보고"로만 쓴다.
- 구독 사용량: 역할 수 × 검토 횟수만큼 늘어난다. 한도·쿨다운이 있지만 사용 패턴에 따라 조정이 필요할 수 있다.
- Stop 신호는 응답이 끝날 때마다 오므로 짧은 대화에서 불필요한 검토가 생기지 않게 `minWrites`가 핵심이다.
